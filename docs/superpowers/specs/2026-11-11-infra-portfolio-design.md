# 인프라·백엔드 겸용 포트폴리오 설계 (Spec)

작성일: 2026-11-11
상태: 사용자 검토 대기

## 1. 목적과 성공 기준

**목적**: 인프라/클라우드/DevOps 직무와 백엔드(Java/Spring) 직무에 모두 지원할 수 있는, 면접용 포트폴리오 저장소 1개를 만든다.

**대상 사용자**: 토목 전공 비전공자, 인프라·개발 실습 경험이 거의 없는 초심자. 백엔드 교육을 병행 중이며 Windows(WSL2) 환경을 쓴다.

**쓸 수 있는 자원**: 주 22시간 × 10주 = 약 220시간 (백엔드 교육 시간 제외).

**성공 기준 (10주차 종료 시점)**
1. 코드를 GitHub에 올리면 자동으로 테스트·빌드·AWS 배포가 된다.
2. 같은 인프라를 Terraform 코드로 만들고 한 번에 삭제할 수 있다.
3. Grafana 화면으로 서비스 상태를 볼 수 있고, 일부러 낸 장애 2~3건의 원인과 해결이 문서로 남아 있다.
4. 본인이 저장소의 모든 코드를 면접에서 설명할 수 있다.
5. README가 직무별 읽는 순서 2가지를 안내한다.

## 2. 접근법과 선택 이유

비교한 3안: (A) 인프라 중심, (B) 백엔드 중심, (C) 서비스 하나로 통일 + 인프라 핵심 2개 집중.

**선택: C안.** 초심자가 10주 안에 끝낼 수 있는 크기로 줄이면서, Spring 서비스를 쓰므로 백엔드 교육과 기술이 통일되고, 인프라 직무에 보여줄 배포 자동화와 장애 대응이 모두 들어간다.

## 3. 범위

**포함**
- Atlas: 장애·운영 지식 기록 서비스 (Spring Boot + PostgreSQL). 기능은 장애 기록의 등록, 목록 조회, 단건 조회, 키워드 검색으로 제한한다. 기록 항목은 제목, 심각도, 증상, 원인, 해결, 작성일이다.
- 배포 자동화: Docker, GitHub Actions(CI/CD), Terraform, AWS
- 관측과 장애 대응: Prometheus, Grafana, 장애 재현 및 문서화

**제외 (10주차 이후 확장 과제)**
쿠버네티스, AI 인프라(Ollama/vLLM), 보안 심화, Vault/MinIO, Ansible

## 4. 구조

흐름: 코드 수정 → GitHub에 올림 → 자동 테스트와 Docker 이미지 생성(GitHub Actions) → AWS 서버에 배포(서버는 Terraform으로 생성) → Prometheus/Grafana로 상태 확인

**저장소**: 새 저장소 1개를 만든다. 서비스가 하나뿐이므로 저장소 루트에 Spring 코드를 둔다. 저장소 이름은 구현 계획 단계의 첫 작업에서 사용자가 정한다.

```
(저장소 루트)
├─ src/ 등        Spring Boot 서비스 코드 (Atlas)
├─ infra/
│   └─ terraform/    서버 생성 코드
├─ monitoring/       Prometheus·Grafana 설정
├─ .github/
│   └─ workflows/    자동 테스트·배포 설정
├─ docs/
│   ├─ incidents/    장애 대응 기록
│   ├─ checklists/   인프라 만들기→확인→삭제 체크리스트
│   └─ learning-log.md
└─ README.md
```

## 5. 10주 일정과 완료 기준

| 주차 | 할 일 | 끝났다고 볼 기준 |
|---|---|---|
| 1~2 | WSL2·Linux·Git 기초, 새 저장소, Atlas 최소 기능 | 내 컴퓨터에서 장애 기록을 등록·조회·검색할 수 있고 GitHub에 올라가 있음 |
| 3 | Docker | 명령어 한 줄로 앱과 DB가 함께 실행됨 |
| 4~5 | CI/CD (GitHub Actions) | 코드를 올리면 자동 테스트와 이미지 생성이 성공함 |
| 6~7 | Terraform + AWS 배포 | 코드로 서버를 만들고, 자동 배포되고, 한 번에 삭제까지 됨 |
| 8~9 | 모니터링 + 장애 대응 | Grafana에 상태가 보이고, 일부러 낸 장애 2~3건을 원인·해결과 함께 문서화함 |
| 10 | 정리와 지원 준비 | README 완성, 구조도 1장, 면접 설명 연습, 지원 시작 |

**조정 규칙**: 일정은 확정이 아니라 기준선이다. 주차 끝마다 학습 일지를 보고 조정한다. 밀릴 때 줄이는 순서는 (1) Atlas 기능, (2) 장애 문서 건수(3건 → 2건), (3) Terraform 범위(서버 1대만)이다. 모니터링과 CI/CD는 마지막까지 지킨다.

## 6. 사고 방지 장치

**요금**
- AWS 계정 생성 직후 예산 알림을 설정한다 (예: 월 5달러 초과 예상 시 이메일).
- 프리티어 범위의 작은 사양만 사용한다.
- 실습이 끝나면 매번 `terraform destroy`로 전부 삭제한다. 삭제 확인을 각 실습의 완료 기준에 포함한다.

**비밀 정보**
- 저장소는 공개를 전제로 한다.
- AWS 키와 DB 비밀번호는 코드에 넣지 않는다. 로컬은 `.env`, 자동 배포는 GitHub Secrets에 보관한다.
- 저장소 생성 첫날 `.gitignore`에 `.env`와 Terraform 상태 파일을 넣는다.

## 7. 품질 확인과 일하는 방식

- Atlas는 핵심 기능에 테스트를 작성하고 CI가 매번 실행한다.
- 인프라는 "만들기 → 동작 확인 → 삭제"를 체크리스트로 `docs/checklists/`에 남긴다.
- Claude Code가 코드를 작성하더라도, 본인이 설명할 수 있는 것만 저장소에 남긴다.
- 주차 끝마다 `docs/learning-log.md`에 배운 것과 막혔던 것을 3~5줄로 적는다.

## 8. README 구성

같은 저장소를 두 방향으로 읽도록 안내한다.
- **인프라/DevOps 지원자용**: 배포 자동화 → 모니터링 → 장애 대응 문서 → Atlas 개요
- **백엔드 지원자용**: Atlas 서비스 코드와 설계 → 테스트 → 배포 자동화
